## Accomplishments

1. **Issue #21 Stage 1 SHIPPED (v3.9.0 + v3.9.1)** -- `GET/POST /redirects`,
   `GET/POST/DELETE /redirects/{id}`, `POST /redirects/bulk`,
   `POST /redirects/preview`. Scoped down from the original proposal with
   user sign-off: `exact`/`prefix` match only (no regex -- ReDoS surface),
   relative targets only (no cross-domain -- open-redirect surface),
   single-hop loop rejection only (`source === target`), no hit_count
   telemetry, no typed-action integration. Option-backed (`rrseo_redirects`,
   no custom table), applied via early `template_redirect:1` hook.
   New `includes/class-rrseo-redirects.php`. 43 new tests (280 -> 323).
   Followed immediately by a **Redirects admin UI page** (v3.9.1,
   read-only table + "Test a URL" tool) matching this panel's existing
   observability-only design -- create/update/delete stay REST-only, same
   as every other data-writing endpoint in the admin panel.
2. **Issue #25 FOUND LIVE + FIXED (v3.9.2)** -- `POST /redirects/bulk` and
   the pre-existing `POST /snippets/bulk` both silently ignored
   `dry_run: true` and persisted writes anyway (the redirects route never
   even registered the arg). A dry-run call would leak state, then the
   follow-up live call on the same payload failed with a false
   duplicate-source error. Both endpoints now register `dry_run` and gate
   the write behind `! $dry_run`. 2 new regression tests (323 -> 325).
3. **Issue #20 FIXED (v3.9.3)** -- `POST /self-update` reported success
   without verifying the install landed (root cause: `RMB_VERSION` is a
   compiled constant that can't detect a same-request change). Now
   re-reads the installed file's version via `get_plugin_data()` and
   compares against the expected version before reporting success;
   returns `500 update_did_not_persist` / `update_verification_failed`
   otherwise. `to_version` on success now reflects the disk-verified
   value. Caveat documented: this only protects updates *from* v3.9.3
   onward -- the update that carries a site *to* v3.9.3 still runs the old
   unfixed code for that one call.
4. **Issues #22/#23/#24 SCOPED via two parallel research forks** before
   any implementation -- ground-truthed each proposal against actual code
   instead of taking the issues' own technical claims at face value. Found
   and corrected: #23's "canonical-dedup is a close precedent" claim
   (it isn't -- single-hook-unhook vs. arbitrary embedded content); #24's
   "`/observe/schema-graph` already renders the page" claim (false -- it's
   a pure meta read); and flagged #22's implied "mostly reuse" as actually
   requiring three genuinely new mechanisms (schema merge-by-type, content
   filter injection, `wp_kses_post` sanitization). User picked the
   recommended option on all three scoping questions.
5. **Issue #24 SHIPPED (v3.10.0)** -- `GET /observe/agentic-browsing/{post_id}`,
   3 static-DOM checks (primary-action detection, schema completeness,
   BreadcrumbList presence) matching PSI's Agentic Browsing sub-audits.
   **Live-verified before writing code**: fetched
   `/observe/heading-hierarchy/2650` against `trevoraspiranti.com`
   (Elementor Pro) with a user-supplied, since-revoked application
   password -- confirmed `apply_filters('the_content', ...)` returns real
   Elementor-rendered HTML (19 content-specific headings) even inside a
   REST request, resolving the main open risk from scoping. Extracted
   `rr_observe_extract_schema_types()` out of the existing
   `/observe/schema-graph` handler so both endpoints share one graph-walk.
   12 new tests (325 -> 337).
6. **Issue #23 SHIPPED (v3.11.0)** -- the simpler variant from the issue's
   own fallback: `strip_third_party` field on the existing
   `POST /schema/{post_id}`, not a separate `/schema-hygiene` resource.
   Implemented as a `wp_head` output-buffer scrub (priority 1 to
   `PHP_INT_MAX`), chosen over Elementor-widget-data parsing because the
   issue's own real-world example (Product schema with populated
   `aggregateRating`) reads like dynamically-rendered widget output, which
   data-parsing would not catch. Plugin's own schema block is now
   bracketed by HTML comment markers and always protected. Whole-block
   removal only (Stage 1 scope). New `includes/class-rrseo-schema-hygiene.php`.
   18 new tests (337 -> 355).
7. **Issue #22 Stage 1 SHIPPED (v3.12.0), Stage 2 split into #26** --
   `GET/POST/DELETE /faq/{post_id}` merges an `FAQPage` schema node onto a
   post's existing graph without disturbing other nodes (`LocalBusiness`,
   etc.) -- required genuinely new read-modify-write logic
   (`rr_schema_merge_node()`/`rr_schema_remove_node_type()`) since
   `rmb_schema_set()` has no merge, only wholesale replace. `answer`
   sanitized via `wp_kses_post` -- a new, stricter sanitization posture for
   this plugin (snippets are intentionally verbatim/unescaped by design).
   Visible Q&A HTML emission deferred to **new issue #26** -- this plugin
   has zero `the_content` filter precedent, and the specific open question
   (hook-priority ordering against Elementor's own content substitution)
   needs live verification before implementation, same as #24 needed.
   New `includes/class-rrseo-faq.php`. 24 new tests (355 -> 379).
8. Suite grew 280 -> 379 tests (99 new) across the session; phpcs clean on
   every commit; every release zip built via the pre-push hook and
   verified (4 structural checks) before push.
