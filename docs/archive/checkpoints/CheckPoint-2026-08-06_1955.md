## Accomplishments (this half-session)

1. **Reviewed outstanding GitHub issues and doc-level technical debt** at
   user's request. Found 3 new issues (#16, #17, #18) filed by an
   external audit pass immediately after #12/#14/#15 closed -- same
   pattern as the audit that originally surfaced #9-#15.
2. **v3.8.1 SHIPPED + CLOSED #16 and #17** -- `POST /media` returned
   `400 rest_missing_callback_param` instead of the documented `422` for
   missing `alt_text`/`source` (fixed: dropped `required: true` from the
   REST-args schema, letting the handler's own validator catch missing
   and empty values identically). `GET /capabilities`'s `Cache-Control`
   header was being silently overridden (root cause corrected mid-fix:
   not kildaybaxter.com's host proxy as first guessed during the v3.8.0
   smoke test, but WordPress core forcing nocache on every authenticated
   REST response -- confirmed by cross-testing on Higgins, a completely
   different host stack, and getting the identical override; fixed via
   a `rest_pre_serve_request` hook, the last filter before output). Both
   live-verified on kildaybaxter.com and higginsoverheaddoor.com after
   self-updating each to v3.8.1.
3. **Found WP Engine has its own, separate Cache-Control override** --
   even after the v3.8.1 fix, Higgins still didn't show `public,
   max-age=60`. Root-caused via WP Engine's own diagnostic headers
   (`X-Cacheable: NO:Passed`, `X-Pass-Why: auth`): their edge layer
   unconditionally rewrites `Cache-Control` on any authenticated request,
   after PHP has already sent the correct header. Confirmed this is
   platform policy, not a plugin bug -- documented in README and
   STARTUP_CONTEXT; #17 closed as fixed regardless (the plugin-level bug
   is genuinely resolved and verified correct pre-WP-Engine-rewrite).
4. **Found and filed #20 (real bug):** `POST /self-update` reported
   `success: true, to_version: 3.8.1` twice on Higgins while `/status`
   never left `3.8.0`. Root cause: `rmb_self_update()` trusts
   `Plugin_Upgrader::install()`'s return value and never re-reads the
   actual installed version from disk. Worked around by having the user
   update manually via wp-admin (which succeeded); the underlying
   false-positive bug is filed and still open, with a well-scoped fix
   proposed (`get_plugin_data()` post-install verification).
5. **Reviewed #18 (`since: null` backfill) -- declined to apply as-is.**
   Its own suggested version-guess table contains a confirmed-wrong entry

   backfill is feasible via `git log -S` archaeology if picked up later.
6. **Filed #19** for the `entity_clarity` README callout that had been
